バックアップから復元した録音195本を、**私が書いたバックアップ処理が消しました。**

ブラウザのバグではありません。自分で書いて、自分でデプロイしたコードです。しかもその30分後に、修正版をデプロイしました。間に合いませんでした。

同じ月、同じアプリで、もう二回やりました。どちらも「あなたのデータは全部守られています」と画面に表示しながらです。

三つとも**守りの側のコード**で起きました。この記事はその三つの記録です。

## 前提を三行で

歌の練習用のPWAを個人で作っています。録音した自分の歌を IndexedDB に保存するアプリです。

そのIndexedDBが、三ヶ月で**22回、中身ごと消えました**（曲もフレーズも録音も全部ゼロになります。原因は今も分かっていません）。

そこで、録音のたびに**端末内の実フォルダへも控えを書く**ようにしました。File System Access API です。ブラウザの割当ストレージの外なので、ここは一緒に消えません。以下はその「控え」をめぐる話です。

:::message
消失そのものの調査 ―― 何が消えて何が生き残るのか、なぜ OPFS が逃げ場にならないのか、`navigator.storage.estimate()` の `quota` を読み違えた話 ―― は[別の記事](https://zenn.dev/imudak/articles/indexeddb-bucket-wiped-22-times)に書きました。この記事はそれを読まなくても通ります。
:::

## 一つ目：掃除が、復元した195本を消しました

バックアップ処理には「掃除」が付いています。IndexedDBから消えた録音の控えを、フォルダからも消す ―― そうしないとフォルダが古いファイルで膨らみ続けるからです。

9月19日の消失のあと、私はこの掃除に安全弁を付けました。

```js
// 初版の安全弁
const catastrophic = wanted.size === 0 && present.size > 0
// 「DBが空っぽなのにフォルダには在る」＝異常。一本も消さずに引き返す
```

ストレージが捨てられた直後はDBが空になります。その状態でフォルダをDBに揃えれば、生き残った控えを全部消してしまう。だから**DBが空のときは掃除しない**。そういう弁です。

これが足りませんでした。

```
09-21 15:21     ストレージの消失（録音 195 → 0）
09-24 02:43:35  ユーザーが3本録音した     ← DBはもう「空」ではない
09-24 02:43:52  バックアップが走った
                 掃除「DBには3本。フォルダの195本は不要な控えだ」
                 → 195本の控えを削除
09-24 03:13     弁を広げた修正版をデプロイ   ← 30分 遅い
```

**一点で張った弁は、現実が半歩ずれただけで素通りします。** DBが「空」から「3本」になっただけで、弁は何の役にも立ちませんでした。

さらに後から分かったのですが、9月19日に控えが助かったのは**偶然**でした。フォルダへのハンドル（これもIndexedDBに住んでいます）が道連れになっていて、同期そのものが走れなかったのです。私はその偶然を、安全弁が効いた証拠だと思っていました。

修正は、弁を**一点から帯へ**広げることでした。

```js
// 「一度に大量を消す掃除」自体を異常の兆候とみなす
const threshold = Math.max(3, Math.floor(present.size * 0.2))
const massCleanup = staleNames.length > threshold
```

「DBが空」という特定の形ではなく、「**消す量が多すぎる**」という形で捕まえます。何が原因でも引っかかります。

## 二つ目：計器が「全部守られています」と嘘をつきました

同じ日、診断情報にこう出ていました。

```
exposure: unbacked=0/199     ← 未バックアップ 0本。全部守られている
lastExportedAt: 2026-09-24T03:04:11
```

ところが **03:04 の時点でDBに在った録音は3本**でした。その後に戻した195本は、どのバックアップにも入っていません。

なぜ「0本」と出たのか。未バックアップの数え方がこうだったからです。

```
最後にエクスポートした時刻より新しい録音 = 未バックアップ
```

これは「**古いものは、あの時のバックアップに入っていたはずだ**」という**推定**です。復元で戻ってきた録音は作成時刻が古いので、「入っていたはず」と数えられました。入っていないのに。

守りは在ったのに、計器が嘘をついていました。そして**計器が嘘をつけば、使う人は安全だと思って何もしません。** 守りは在っても働きません。

直し方は、推定をやめて**台帳を持つ**ことでした。「どの録音が現に外に在るか」をIDで記録する。時刻ではなく身元で数える。

## 三つ目：同じ計器が、もう一度嘘をつきました

台帳は、フォルダの実情で照合しないと腐ります。同期のたびにフォルダを一覧し、そこに無いIDは「外に在る」印を落とす ―― そうしないと、一つ目のような事故に気づけないからです。

10月7日、使っている人からこう言われました。

> 今日バックアップして、それから55本も録っていないのに「未バックアップ 55本」と出るのは何故ですか

録音が増えたのではありません。**台帳の印が剥がされていました。**

```js
// フォルダを一覧して、その結果を呼び出し元へ返す
res.presentIds = [...(after ?? [])].map(toRecordingId).filter(Boolean)
//                        ^^^^^^^
//                        一覧に失敗して null が来たとき、
//                        これは [] になる ＝「検めた。フォルダは空だった」
```

フォルダを開く権限は、ユーザー操作のたびに要求します。録音のたびに走る自動同期は、そのセッションでまだ許可を取っていなければ**ディレクトリを開く時点で失敗します**。そのとき返り値の初期値が `presentIds: []` でした。

呼び出し元は `[]` を受け取り、「フォルダは空だ」と読み、**フォルダに199本が現に在るまま、台帳の印を全部剥がしました。**

「読めなかった」が「空だった」に化けていたのです。

直したのは二箇所です。

```js
// ① 初期値から外す。undefined ＝「まだ検めていない」
//    呼び出し元の if (res.presentIds) が、ここで初めて意味を持つ

// ② 書くべきものが在ったのに一つも見えない、は「空」ではなく「異常」
//    この関数は無いファイルを*書いてから*数えるので、
//    実在0 は「空になった」ではなく「書き込みが全部失敗した」か「一覧が嘘をついた」
if (ids && !(ids.length === 0 && wanted.size > 0)) res.presentIds = ids
```

この形の間違いは、半年前にも一度やっていました。フォルダに置き場所を作れなかったとき、失敗数 `failed: 0` のまま黙って返していて、呼び出し元が `failed === 0` を成功と読んでいた。**一本も書かずに「成功しました」と名乗る守り**です。

**「何もしなかった」を「成功」と呼ばない。「読めなかった」を「空」と読まない。** 同じ掟の、違う顔でした。

## 三つに共通していたこと

| 何が起きたか | 本当の問題 |
|---|---|
| 掃除が控えを消した | 弁を「最悪の一点」で張っていた（半歩ずれたら素通り） |
| 「0本」と嘘をついた | **推定**を測定値のように見せていた |
| 「55本」と嘘をついた | **失敗**を測定値（空）として扱っていた |

三つとも守りの側のコードです。消失そのものより、こちらのほうが怖いと思っています。消失は外から来ますが、これは自分で書いて自分でデプロイしています。しかも**使う人には「守られている」と見える顔をしている**ぶん、気づかれません。

**守りは、守る対象を壊す力を併せ持ちます。** 削除する力・数を告げる力を持つ経路には、それ自体を疑う弁が要ります。

## 持ち帰ってもらえるとしたら

**削除する経路の弁は、一点ではなく帯で張る。** 「最悪の形」を名指しで防ぐと、現実が半歩ずれたときに素通りします。「消す量が多すぎる」のように、原因を問わない形で捕まえるほうが保ちます。

**「安全です」と告げる数字は、推定ではなく実測で出す。** 時刻の比較で「入っているはず」と数えるのは推定です。IDで「現に在る」と数えるのが実測です。推定を測定値の顔で見せると、使う人はそれを信じて何もしません。

**失敗を、測定値として扱わない。** 「読めなかった」は「空だった」ではありません。戻り値の初期値（`[]`・`0`・`false`）が、そのまま「検めた結果」として下流に流れる形になっていないか確かめてください。私の場合、`[]` が「空のフォルダ」に化けて台帳を壊しました。

分からないまま守りを作ると、守りの数だけ新しい壊し方が増えます。それでも作るしかないのですが、**作った守りは、守る対象と同じくらい疑ったほうがいい** ―― というのが、三ヶ月でいちばん高くついた教訓でした。
