「IndexedDBが消えるなら、OPFS へ逃がせばいいのでは」

私はそう考えて、実際に移行を検討しました。結論を先に書くと、**なりませんでした。** OPFS に生存確認の印を置いて実測したら、IndexedDBが消えるたびに、その印も一緒に消えていました。

理由は単純です。**IndexedDB と OPFS と CacheStorage は、同じ一つの箱の中に置かれています。** そして消えるときは、箱ごと消えます。

この記事は、その「箱」が何なのかという話です。あわせて、私が二ヶ月近く取り違えていた `navigator.storage.estimate()` の `quota` についても書きます。

## 前提を三行で

歌の練習用のPWAを個人で作っています。録音した自分の歌を IndexedDB に保存するアプリです。

そのIndexedDBが、三ヶ月で**22回、中身ごと消えました**。曲もフレーズも録音も全部ゼロになります。最も多いときで録音195本。**原因は今も分かっていません。**

逃げ場を探して OPFS を検討し、カナリア（生存確認の印）を置いて実測しました。以下はそこで分かったことです。

## 消えるとき、何が消えて何が残るか

消失のたびに採れるよう、OPFS と CacheStorage に印を置いておきました。消失の瞬間の記録はこうです。

```
IndexedDB        → 空
OPFS カナリア     → LOST（領域は開けたが印が無い）
区画カナリア      → LOST（CacheStorage。同上）
localStorage     → 生きている
刻みの成否        → failedAt=(none)（刻めなかったのではない）
persisted        → true
```

**三つが揃って更地になり、localStorage だけが生き残ります。** しかも印は「刻めなかった」のではなく「刻んだものが消された」。この区別のために、印を**書けたかどうか**の台帳も別に取っていました。

手元のログに残る8件（上限10件で古いものから捨てられます）は、**8件とも同じ署名**でした。前回はきれいに `db.close()` まで到達して終わっており、その後アプリは一度も開いていません。**誰も触っていない数時間に、これが起きます。**

`localStorage` が22回とも生き残ったことの証拠は、**消失が22回とも記録に残った**こと自体です。消失を検知したときの書き込み先が localStorage なので、そこが死んでいれば記録は残りません（ログは上限10件で、古いものは捨てられます。22件ぶんは別のノートへ移してあります）。

## なぜ三つが同時に消えるのか ―― オリジンとバケット

まず**オリジン**から。ドメインに似ていますが、もう少し厳しい単位です。**スキームとホストとポートの三つ組**で、三つとも一致して初めて「同じオリジン」になります。

| | 同じオリジンか |
|---|---|
| `https://example.com` と `http://example.com` | **別**（スキームが違う） |
| `https://example.com` と `https://app.example.com` | **別**（ホストが違う） |
| `https://example.com` と `https://example.com:8443` | **別**（ポートが違う） |

**ブラウザの保存領域は、このオリジンごとに完全に分かれています。** 別のオリジンなら、棚も、バケットも、localStorage も、まるごと別物です。

これは私の調査でも効きました。途中で置き場所を自宅サーバ（`…ts.net:8443`）から Vercel（`utaloop.vercel.app`）へ移したのですが、**消失ログも別々に積まれます**。移した先の記録だけを見て「静かになった」と思っていたら、古い方に7日間読まれないまま1件積まれていた、ということがありました。

さて、バケットの話です。Storage Standard では、ブラウザはオリジンごとに**棚**を持ち、その棚に**バケット**が並ぶ、と定めています。何もしなければバケットは**一つだけ**で、それが**既定バケット**です。

**IndexedDB・CacheStorage・OPFS は、それぞれ独立した保管庫ではありません。** どれも「既定バケットの中の一区画」として置かれています。

```
オリジン（https://example.com）
  └ 既定バケット          ← 容量の割当・永続性・退去の判定は、この単位で行われる
      ├ IndexedDB
      ├ CacheStorage
      └ OPFS
```

**退去（eviction）も削除も、この箱の単位で起きます。** 中身を一つだけ選んで捨てる仕組みではありません。だから「IndexedDB が危ないので OPFS へ」は、**同じ箱の中での引っ越し**にしかなりません。

実機で中を覗きたいときは `chrome://quota-internals` を開くと、バケットの一覧と最終更新が見られます。

## `persisted: true` は「消えない」ではありません

永続化のメソッドは二つに分かれています。**要求するのが `navigator.storage.persist()`、いまの状態を読むのが `navigator.storage.persisted()`** です（どちらも `Promise<boolean>`）。状態を知りたいだけなら後者を呼びます。

要求が通ると、この既定バケットが persistent になります。ただし仕様上これが守るのは**容量逼迫による自動退去**からであって、あらゆる消え方を防ぐものではありません。

**私の22回は、すべて `persisted: true` の状態で起きています。**

## 名前付きバケットも、同じ層の下です

**Storage Buckets API**（`navigator.storageBuckets.open()`）を使えば、名前付きのバケットを追加で作れます。バケットごとに永続性や期限を分けられるのですが、**同じ quota の層の下にある**ので、「別のバケットへ逃がせば助かる」とは考えにくく、私は採りませんでした。

一方 **localStorage** は、仕様の上では同じ棚の住人として書かれています。けれど Chromium の実装では別系統の保存庫に置かれており、名前付きバケットへ分割することもできません。**私の22回で localStorage だけが生き残ったのは、この実装上の分離とよく符合します** ―― ただし、仕様がそれを保証しているわけではありません。

ですので私は、消失ログと構造の控えを localStorage に置いています。**消える側に記録を置くと、記録ごと消えるので。**

## おまけ：`quota` は端末の空き容量ではありません

ここは完全に私の読み違いの話ですが、同じ間違いをしている人がいるかもしれないので書いておきます。

調査のあいだ、私はずっと診断情報にこう書いていました。

```
pressure: usage=0MB quota=10240MB (0%)
```

**「ストレージ逼迫度 0%」。空きは十分にある。だから容量の問題ではない。** ―― 17件ぶんの調査記録に、私はそう書き続けていました。

これが間違いでした。

この数字は `navigator.storage.estimate()` の `usage` と `quota` です。そして **`quota` は端末の空き容量ではありません。** あれは「このオリジンが使ってよい上限」であって、Chromium が計算して割り当てた数字です。**端末そのものの空きとは、別の物差しです。**

`chrome://quota-internals` を実機で開いて、初めて本当の数字を見ました。

```
端末の総容量 : 109.47 GB
端末の空き   : 1.58 GB（1.4%）
```

**端末はほぼ満杯でした。** 「空きは9割以上ある」どころか、残り1.4%です。

Web の API からは端末の空き容量は読めません。だから診断パネルにも出せず、私は代わりに**読める数字を見て、読めない数字を見た気になっていました。**

（なお、その後に空きを 7GB まで空けて3週間消失が止まり「容量が原因だった」と思ったのですが、それも**間違いでした**。空きが4倍になった状態で、録音195本が消えました。この二度目の読み違いは[長い方の記事](https://zenn.dev/imudak/articles/indexeddb-bucket-wiped-22-times)に書いています。）

## では、逃げ場はどこにあるのか

**箱ごと捨てられるのなら、逃げ場は箱の外にしかありません。** 置き場所を「誰が触れるか」で並べるとこうなります。

| 置き場所 | アプリから | 使う人から | ブラウザ / OS から |
|---|---|---|---|
| 既定バケット（IndexedDB・OPFS・CacheStorage） | いつでも読み書き | 見えない | **予告なく丸ごと捨てられる** |
| localStorage | いつでも読み書き | 見えない | 実測では捨てられなかった |
| 端末の実フォルダ（File System Access API） | **許可をもらった時だけ**書ける | ファイルアプリで見える | 捨てない |
| zip（端末の外） | 書き出すだけ | 自由に扱える | 関与しない |

私は下の二段を作りました。**①録音のたびに端末内の実フォルダへも控えを書く**（File System Access API。置き場所を一度選んでもらえば以降は自動）、**②zip で端末の外へ書き出す**（機種変更や端末そのものを失う備え）。

①は実際に働きました。9月19日に録音195本が消えたとき、**フォルダの控えが箱の外で生き延びていて、195本すべてが戻りました。**

ただし、その控えを作る側のコードで私は三回事故を起こしています。掃除が復元した195本を消し、計器が二度「全部守られています」と嘘をつきました。そちらは[バックアップ処理が、バックアップを消しました](https://zenn.dev/imudak/articles/backup-code-deleted-the-backup)に書きました。

ここで効いてくるのが上の表の**右の二列**です。バケットの中身は、消えるまで**誰の目にも触れません**。使う人は自分のデータがどこにあるのか見えないし、消えたことにも気づけない。**フォルダへ出した瞬間に、初めて「自分で扱えるもの」になります。**

## 持ち帰ってもらえるとしたら

**OPFS は IndexedDB のバックアップ先になりません。** 同じ既定バケットの住人で、捨てられるときは箱ごとです。名前付き Storage Bucket も同じ quota の層の下にあります。逃がすなら、箱の外（端末の実フォルダ・端末の外）へ。

**`persisted: true` は「消えない」ではありません。** 防いでくれるのは容量逼迫による追い出しだけです。私の22回はすべて `persisted: true` で起きました。

**`navigator.storage.estimate()` の `quota` を端末の空き容量として読まないでください。** あれはオリジンへの割当です。混同すると、「容量は十分だ」という誤った前提の上に調査を積み上げることになります（私は17件ぶんやりました）。端末の空きは Web の API では届きません。開発中なら `chrome://quota-internals` で見られます。

**消失ログは、消える側に置かないでください。** 記録ごと消えます。私の場合は localStorage が生き残ったので、そこに置いています（仕様の保証ではなく、22回ぶんの実測です）。
